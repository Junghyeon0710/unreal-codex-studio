# ue-feature

Read architecture and define observable acceptance. Follow the manager's
[adaptive workflow](../../../docs/feature-loop.md): choose the smallest sufficient
roster, scopes, dependencies and useful checks for this request. Do not turn the
five-worker door example into a universal requirement. Narrow work may need one
expert; the Astra manager decides staffing without asking routine roster questions.
Use actual host calls for selected specialists with their configured or
host-resolved inherited models; never force shipped Sol after an override or invent
worker IDs. Unsupported model IDs are explicit host/provider failures.
Assigned workers stay within scope without recursively launching another team.

Select independent review when useful, requested or claimed; the reviewer must
not approve its own work. Return actual findings to the author and obtain renewed
review when selected. Bound repairs; never manufacture defects. Choose editor,
build, packaging and gameplay QA only when they meaningfully apply. For editor
work, one owner exclusively controls official MCP, assets and PIE; preserve project
binding and host permissions. Compilation alone is not gameplay evidence.

For tracked handoffs, optionally use tools/studio_pipeline.py with selected roles,
stages/checks and reasoned plan changes. Preserve previous outcomes and changed
acceptance honestly. Explanation/read-only requests do not need a journal or an
implementation team. Report observed results, missing tools and material limits.
